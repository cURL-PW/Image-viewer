# 設計メモ

実装上の判断とその理由です。仕様は [SPEC.md](../SPEC.md) を参照してください。

- **SQLite は Electron 内蔵の `node:sqlite` を使用** — ネイティブモジュールの再ビルドが不要になり、配布時の環境依存を減らせます。実験的 API のため起動時に警告が出ますが動作に影響はありません
- **推論は utilityProcess で実行** — onnxruntime と sharp の重い処理をメインプロセスから切り離し、UI の応答性を保ちます
- **画像は ID でのみ参照** — renderer にはファイルパスを渡さず、`app-image://` プロトコル側でルート配下かを検証してから配信します
- **並び順は自然順** — `p2.jpg` が `p10.jpg` より前に来るよう、DB に自然順ソート用のキーを持たせています
- **HEIC は WASM で復号** — sharp のプリビルドに含まれる libheif には HEVC デコーダ (libde265) が
  無く、コンテナは読めても画素まで復号できません。`src/main/images.ts` が WASM 版 libheif での
  復号と EXIF orientation の適用を引き受け、他のコードは形式を意識せずに済むようにしています
- **派生画像の生成は同時 2 件まで** — libuv のスレッドプールは既定 4 本で、Electron 起動後に
  `UV_THREADPOOL_SIZE` を変えても効きません (実測で確認)。遅い読み込みが並ぶとプールが埋まり、
  フォルダ走査まで巻き添えで止まるため、`src/main/semaphore.ts` で常に空きを残しています
- **クラウド同期フォルダは門番を通す** — `src/main/cloud-guard.ts` が読み込みの可否を決めます。
  Windows では `src/main/win-placeholders.ts` がファイル属性から未ダウンロードの一覧を作るので、
  1 枚も落とさずに個別で弾けます。ユーザーが明示的に開いた 1 枚と一括ダウンロードは素通りさせます
- **「案内」と「遮断」は別の状態として持つ** — 一覧が作れても遮断器は解除しません。
  一覧は 1 枚ずつ弾くため、遮断器は取りこぼしたときに最後で止めるためのものです。
  混ぜると「案内は出ているのに読み込みは止まっていない」状態が起こりえます
- **走査の `fs.stat` は読み込みとは別の遮断器にかける** — 実測した iCloud の
  プレースホルダは `RECALL_ON_DATA_ACCESS` (データを読んだときだけ実体化) なので、
  `stat` ではダウンロードは起きません。日付やサイズが取れると並べ替えができるので
  既定では stat し、遅い状態が続いたら (`RECALL_ON_OPEN` を使う同期クライアントの
  可能性) stat だけをやめます
- **ファイル監視は OS 標準の再帰監視 (`fs.watch` の `recursive`)** — chokidar は
  やめました。9 万枚のフォルダで計測したところ、**監視の準備だけで 1 ファイルにつき
  stat 2 回 (計 18 万回) と監視ハンドル 9 万個**を作り、11〜25 秒と 400MB を使います。
  Windows の libuv は stat をファイルの `CreateFileW` で実装するため、これは
  「起動のたびに全ファイルを開く」動作になり、クラウドの実体取得を誘発します。
  再帰監視ならハンドルは 1 つで、準備中にファイルを触りません
  (回帰テスト: `npm run test:scale`)
- **ファイルに触れた操作はログに残す** — `src/main/debug-log.ts`。走査・監視・サムネイル・
  推論・プロトコル配信のすべてに所要時間付きで 1 行ずつ残します。推測ではなく実測で
  「どの経路がダウンロードを起こしているか」を突き止めるためのものです
